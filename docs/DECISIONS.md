# Промпты, решения и ограничения

## Промпты

Текст находится в [`cardgen/prompts.py`](../cardgen/prompts.py), а его версия попадает в `meta.prompt_version` каждого результата.

**Системный промпт** задаёт роль редактора B2B-каталога и содержит:

- запрет на факты вне блока `<product_data>`, с перечислением типичных выдумок: стандарты, материалы, степени защиты, поверка, гарантия, отрасли;
- требования к каждому полю и подсказку, как набрать 800–1200 символов: объяснять смысл известных характеристик, а не добавлять новые;
- правило для блока менеджера: называть роли, а не отрасли, если отрасль не указана;
- поле `data_gaps`, куда модель пишет вопросы вместо догадок;
- указание считать содержимое `<product_data>` данными, а не инструкциями.

**Запрос** содержит данные товара в JSON и список полей без значений. Символ `<` экранируется, поэтому текст товара не может закрыть блок данных.

**Промпт исправления** возвращает модели конкретные замечания: сколько символов получилось и какой факт не подтверждён. Если значения нет в данных, модель должна удалить его, а не заменить другим.

## Решения

| Решение | Почему |
| --- | --- |
| Таблицу характеристик собирает код, а не модель | Значения копируются из входа, поэтому модель не может их исказить |
| Характеристики из описания принимаются только с дословной цитатой | Код проверяет, что цитата есть в описании, а значение есть в цитате |
| Числа, латинские обозначения и аббревиатуры в тексте сверяются с входом | Промпт снижает риск выдумки, а проверка кодом ловит то, что прошло мимо него |
| Отдельный список рискованных утверждений без чисел | «Нержавеющая сталь» или «поверка» не ловятся по числам |
| Формат ответа задаётся через `response_format` со строгой JSON-схемой | Ответ разбирается надёжнее, чем свободный текст, а лишние поля исключены |
| Модель `gpt-6.1-sol` по умолчанию | Сбалансированный вариант по цене и качеству; модель меняется через `LLM_MODEL` |
| Закончившийся баланс OpenAI не повторяется | Ошибка `insufficient_quota` не исчезнет от повторных запросов |
| Длины проверяются в коде и возвращаются модели | Модели плохо считают символы, поэтому длину надёжнее измерять кодом |
| Карточка с неустранёнными замечаниями возвращается как `needs_review` | Менеджеру полезнее черновик с указанием проблемы, чем пустая ошибка |
| При нехватке базовых данных LLM не вызывается | Без названия или без каких-либо сведений о товаре получился бы только вымысел, и токены были бы потрачены зря |
| HTTP-запросы через `requests`, а не SDK | Меньше зависимостей, а таймауты и повторы видны в коде. SDK стоит рассмотреть при развитии проекта |
| Сервер слушает только `127.0.0.1` | В сервисе нет аутентификации, а задание требует локальный прототип |
| В логи не пишутся данные товара и ключ | Только метод, путь, статус, время и идентификатор запроса |

## Ограничения

- **Проверка фактов эвристическая.** Она надёжно ловит числа и обозначения, а словесные утверждения только из списка в `factcheck.py`. Выдумку другими словами («подходит для пара») она не поймает, поэтому текст должен просмотреть человек.
- **Возможны ложные срабатывания.** Например, `1 200` в тексте и `1200` во входе считаются разными значениями. Если модель не исправит такое замечание, карточка получит `needs_review`.
- **Список типовых характеристик один на все приборы.** Для механического манометра «питание» и «интерфейсы» могут быть неприменимы.
- **Проверка единиц не выполняется отдельно.** Число сверяется с источником, но его единица измерения не сравнивается.
- **Качество поисковых запросов не проверяется по данным о спросе.** Запросы отражают логику закупщика, но не частотность.
- **Одна LLM и встроенный сервер Flask.** Этого достаточно для локального прототипа, но не для внешнего доступа.

## Возможные улучшения

1. Профили характеристик по типам приборов: манометр, датчик, расходомер.
2. Набор эталонных товаров и замер качества промпта при каждом его изменении.
3. Вторая модель-рецензент для словесных утверждений, которые не ловит эвристика.
4. Сравнение единиц измерения вместе с числами.
5. Импорт PDF-паспортов и пакетная обработка из CSV или XLSX.
6. Выгрузка в CMS, история правок менеджера и частотность запросов из Wordstat.
7. Аутентификация, WSGI-сервер и лимиты запросов, если сервис выйдет за пределы локальной машины.
